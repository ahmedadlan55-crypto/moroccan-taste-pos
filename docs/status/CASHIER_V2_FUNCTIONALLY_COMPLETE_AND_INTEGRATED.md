## 1. الخلاصة التنفيذية

كاشير V2 **مكتمل وظيفيًا ومدمج داخل النظام الرئيسي نفسه**: تطبيق React لمس-أولًا/Offline-أولًا على `/pos-v2` بجانب `/pos` القديم (مسار الrollback)، بطبقة backend رفيعة تملك دورة حياة السلة فقط بينما **المال لا يمر إلا عبر مسار البيع القديم المجرّب** (`POST /api/sales`: ZATCA + GL + خصم المخزون/الدفعات + الورديات) بمفتاح `clientOrderId` = ULID الطلب — فلا ازدواج دفع ولا ازدواج خصم مخزون بأي سيناريو (إعادة محاولة/أوفلاين/تزامن).

## 2. المعمارية

- **Repository/Express/DB/Auth واحد** — Vite app ثانٍ في `frontend/pos` يُبنى في نفس صورة Docker (مرحلة رابعة) ويُخدم من نفس السيرفر خلف CSP صارمة وflag `POS_V2_ENABLED` (افتراضي: مفعّل خارج الإنتاج، معطّل في الإنتاج حتى أمر صريح).
- **Backend**: `routes/pos-v2.js` تحت `/api/pos/v2` — دوال `do*()` داخلية موحدة تخدم HTTP و`/sync` معًا (مسار منطق واحد). `lib/posOrderMachine.js` آلة نقية مختبرة.
- **نفس token** (`pos_token`) — تنقل حر بين الكاشير القديم والجديد والنظام الرئيسي بلا login ثانٍ؛ رابطا "العودة للنظام الرئيسي" و"الكاشير القديم" في الهيدر.

## 3. State Machine (pos_orders.status)

```
open ⇄ held (تعليق/استعادة — بلا أثر مالي)
open → submitted (تجميد الدفعات + بناء legacyPayload) → completed (ربط sale_id)
submitted → open (reopen — فشل/إلغاء الدفع؛ تُمسح الدفعات)
open|held → voided (سبب إلزامي — قبل المالية فقط؛ بعد الإكمال يمر عبر
                    الإشعار الدائن الرسمي /api/sales/:id/void|return حصريًا)
```
- **منع double payment**: `clientOrderId` UNIQUE في sales (replay idempotent مثبت) + Idempotency-Key على submit + version على كل تحديث.
- **منع duplicate receipt/stock**: البيع يُكتب مرة واحدة فقط عبر المسار القديم؛ V2 لا يلمس المخزون إطلاقًا.

## 4. Business Rules المطبقة (سيرفريًا — ليست إخفاء أزرار)

| القاعدة | التطبيق |
|---|---|
| لا دفع بلا وردية مفتوحة | doSubmit يرفض (422) — والوردية تُفتح/تُغلق عبر endpoints القديمة v7.5 |
| مجموع الدفعات = الإجمالي بالضبط | PAYMENT_MISMATCH (الباقي عبر cashTendered) |
| سقف خصم الكاشير | POS_MAX_CASHIER_DISCOUNT_PCT (افتراضي 10%) — تجاوزه 403 لغير المشرف |
| البيع الآجل بمشرف | credit → PERMISSION_DENIED للكاشير |
| عزل الملكية | الكاشير يرى/يعدل طلباته فقط؛ المشرف يرى الكل |
| الأسعار والضريبة من الخادم | lines تُطبَّع ضد menu الحية (نشاط الصنف + tax_category) والإجماليات تُحسب سيرفريًا |
| VAT شامل بفئات S/Z/E/O | مرآة رياضية مطابقة بين العميل والخادم (اختبارات متطابقة) |
| Offline آمن | كاش فقط؛ ممنوع: شبكة/مختلط/آجل/إلغاء مُزامَن/فتح-إغلاق وردية |
| تعارض النسخ | نسخة الخادم تفوز؛ المحلي يُركن كمسودة جديدة + إسقاط العمليات التالية |

## 5. Database changes (idempotent)

`pos_orders` (id=ULID العميل PK، status ENUM، order_type، table_no، shift_id نصي يطابق SH-*، username/device، discount_*، إجماليات، sale_id/invoice_number، origin online/offline، version، طوابع المراحل) + `pos_order_lines` (لقطة اسم/سعر/خصم/فئة ضريبية) + `pos_payments`. **صفر تعديل على جداول legacy.**

## 6. APIs — `/api/pos/v2`

`GET /catalog` (ETag/304) · `GET /orders` (+status/shift، عزل ملكية) · `GET /orders/:id` · `POST /orders` (upsert: إنشاء idempotent بالULID / تحديث version-guarded) · `POST /orders/:id/hold|resume|reopen|void` · `POST /orders/:id/submit` (Idempotency-Key → legacyPayload) · `POST /orders/:id/complete` (ربط sale_id بتحقق تقاطعي + replay) · `POST /sync` (دفعي، dedupe بـ opId، أخطاء لكل عملية) · `GET /shift-summary/:shiftId`.

## 7. الواجهة (frontend/pos — 41 ملفًا)

شاشة واحدة: فئات + شبكة منتجات (بحث فوري + مسح باركود بEnter) + سلة (كمية/ملاحظات/خصم سطر/نوع طلب وطاولة/عميل/خصم فاتورة مع تحذير السقف) + حوارات: دفع (كاش بأزرار استلام سريعة وباقٍ محسوب/شبكة/مختلط بتحقق حي/آجل بمشرف؛ تقدّم مراحل الدفع؛ نجاح بفاتورة وطباعة إيصال RTL + تذكرة مطبخ)، معلقة (خادم+محلي)، وردية (فتح/إغلاق close-v3 بشبكة فروقات حية لكل الطرق)، إلغاء بسبب، تقرير مزامنة. مؤشر اتصال (متصل/غير متصل+عدّاد/مزامنة). اختصارات F2/F4/F9/Esc، لمس ≥44px، استجابة 1024/768/375px، **أرقام إنجليزية حصريًا**، وطباعة تذكرة مطبخ تُعرض بعد التعليق أيضًا.

## 8. Offline (المعمارية المنفذة)

IndexedDB (غلاف داخلي بلا اعتماديات): كتالوج بـ ETag + مستندات الطلبات + طابور FIFO. كل تغيير يُحفظ محليًا فورًا ثم upsert مدين 600ms. **مسار دفع واحد** online/offline: الطابور يشغّل سلسلة submit→sales→complete بمفاتيح idempotent (opId + clientOrderId) — انقطاع منتصف السلسلة يُستأنف بلا ازدواج (مثبت E2E: مزامنة "مرة واحدة بالضبط"). حقل `serverVersion` مملوك للمحرك ويُدمج قبل أي كتابة لمستند UI (إصلاح جوهري اكتشفه E2E ووثّقه commit 705bc02).

## 12. المخاطر المتبقية والتشغيل

- **Production**: التفعيل يتطلب قرار مالك (`POS_V2_ENABLED=1`) — حتى حينها `/pos` القديم يبقى كما هو (rollback فوري بإزالة العلم). لا هجرة بيانات مطلوبة (جداول جديدة فقط).

- مودفَيرز/كومبو صريحة غير موجودة في النظام أصلًا (تُحاكى بالوصفات كما في القديم) — خارج نطاق المطابقة الوظيفية الحالية، وملاحظات السطر تغطي الطلبات الخاصة.
- إشعار دائن (void/return) بعد الإكمال يبقى من شاشات الإدارة القديمة (بموافقة مدير) — قرار معماري مقصود ومُوثق في الواجهة برسالة توجيه.
