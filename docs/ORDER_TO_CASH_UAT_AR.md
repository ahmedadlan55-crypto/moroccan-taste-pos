# خطة قبول المستخدم (UAT) — Order-to-Cash

> تُنفَّذ محليًا/اختبارًا مع `ORDER_TO_CASH_ENABLE=1` وجلسة حقيقية. كل خطوة لها نتيجة متوقعة قابلة للتحقق.

## التهيئة
1. `npm run o2c:migrate` (apply) ثم rerun نظيف. 2. `npm run build:sales`. 3. تشغيل الخادم بالعلم ON. 4. تسجيل الدخول من التطبيق الأساسي (نفس الجلسة).

## سيناريوهات القبول
| # | السيناريو | المتوقع |
|---|---|---|
| 1 | الدخول ومشاهدة القائمة الرئيسية | قسم واحد «المبيعات والعملاء»؛ لا مداخل مبيعات/عملاء/ذمم قديمة |
| 2 | الضغط على القسم | يفتح `/sales` (نفس التبويب) بلا تسجيل دخول ثانٍ |
| 3 | العلم OFF | القسم يختفي والقديم يعمل كما هو (عكسي) |
| 4 | إنشاء عميل (B2B + رقم ضريبي + حد ائتمان + شروط) | يُحفظ ويظهر في القائمة؛ الأرقام إنجليزية |
| 5 | فتح Customer 360 | رصيد/حد/تعرّض/أعمار حسب الاستحقاق/فواتير/تحصيلات/كشف حساب |
| 6 | إنشاء أمر بيع ← تأكيد | Stepper يتقدّم؛ الآجل بلا عميل يُرفض من الخادم (422) |
| 7 | تفويتر الأمر ← إصدار الفاتورة | فاتورة صادرة + قيد GL + UUID زاتكا؛ لا زر تعديل |
| 8 | تسجيل تحصيل جزئي وتخصيصه | الفاتورة تصبح «مدفوعة جزئيًا»؛ منع over-allocation |
| 9 | تسجيل باقي التحصيل | الفاتورة «مدفوعة» |
| 10 | إنشاء مرتجع جزئي من الفاتورة ← ترحيل | إشعار دائن مرتبط + قيد عكسي append-only |
| 11 | عكس تحصيل مُرحّل | حالة «معكوس» + قيد عكسي (لا حذف) |
| 12 | طباعة الفاتورة وكشف الحساب | تخطيط A4 نظيف بلا تنقّل |
| 13 | التقارير (14 نوعًا) + فلاتر + CSV + طباعة | جداول صحيحة، أرقام إنجليزية، تصدير يعمل |
| 14 | مستخدم بلا صلاحية | 403/PermissionDenied دون انهيار |
| 15 | الأرقام في كل الشاشات | 0-9 إنجليزية دائمًا (لا ٠١٢٣) |

## معايير النجاح
- صفر أخطاء console حرجة، صفر تجاوز أفقي، كل القوائم تعرض المحتوى فور الضغط.
- كل mutation يحمل Idempotency-Key؛ التقادم يعطي 409 مع رسالة «أعد التحميل».
- القديم مخفي عند ON ويعمل عند OFF (عكسي بتغيير علم واحد).
