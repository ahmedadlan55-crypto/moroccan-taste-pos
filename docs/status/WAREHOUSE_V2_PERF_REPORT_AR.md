## 3) الفهرس المُضاف (بدليل EXPLAIN — الوحيد)

**`idx_invmov_item_wh_date` على `inventory_movements (item_id, warehouse_id, movement_date)`** — هجرة idempotent في `server.js`.

- **السبب المُقاس:** استعلامات فرعية مرتبطة (last_movement في الشبكة + out_qty/last_movement في محرك إعادة الطلب) تنقّب `inventory_movements` بـ(صنف،مستودع،تاريخ) ولم يكن يغطيها إلا فهرس أحادي العمود.
- **الدليل قبل/بعد (100k حركة):** grid sort=qty **1.93s → 0.60s** · Replenishment كامل **3.1s → 1.03s** (ولمستودع واحد **0.16s**) · زمن بناء الفهرس **0.8s** (online).
- فهارس أخرى **لم تُضف عمدًا**: تحذيرات EXPLAIN المتبقية (مسح كامل في lot-integrity وقائمة expiry) هي فحوص/لوحات شاملة بالتصميم وأزمنتها مقبولة (335ms/787ms) — إضافة فهارس لها بلا أثر مُقاس مخالفة لقاعدة «فهرس بدليل فقط».

## 4) تحقّق نطاق assertInvariant

`lib/lotLedger.js::assertInvariant` يعمل على **الزوج المتأثر فقط (صنف، مستودع)** عبر استعلامين مفهرسين (`idx_wlb_wh_item`) — **ليس فحصًا شاملًا بعد كل حركة**. الفحص الشامل متاح فقط عند الطلب عبر `GET /lot-integrity` (335ms على 50k مجموعة) وأمر preflight.

## 5) ملاحظات وقيود (تُدار في سجل المخاطر)

1. **Analytics 1.28s** و**Expiry 0.79s**: تجميع كامل الحجم في صفحات كسولة التحميل — مقبول للإطلاق؛ تحسين لاحق مقترح: تجميع مسبق/كاش قصير.
2. **Replenishment بلا فلتر** يحمّل كل الصفوف ثم يقسّم صفحات في التطبيق (997ms عند 50k) — الواجهة تمرر مستودعًا دائمًا (160ms)؛ يُوصى بدفع LIMIT إلى SQL في مرحلة لاحقة.
3. **استجابة lot-integrity 3.6MB** (كل المجموعات) — أداة تشغيلية إدارية؛ يُوصى بترقيم صفحاتها لاحقًا، وموجودة أيضًا كـCSV وpreflight.
4. القياسات محلية أحادية العقدة؛ أرقام الإنتاج ستتأثر بالشبكة/القرص — المنهجية قابلة لإعادة التشغيل كما هي (`npm run perf:warehouse-v2`).
