# Runbook التراجع (Rollback) — Warehouse V2 · المرحلة 5A

> **المبدأ:** التراجع مُصمَّم على ثلاث درجات متصاعدة — عطّل أولًا، تراجع بالكود ثانيًا، واستعادة القاعدة آخر الحلول. الهجرات **إضافية فقط** (لا حذف/تغيير بيانات قديمة)، لذا الرجوع بالكود آمن دون لمس المخطط.

## الدرجة 1 — تعطيل فوري بلا نشر (ثوانٍ، بلا فقد بيانات)

```
WAREHOUSE_V2_ENABLED=0   → إعادة تشغيل الخدمة
```
- الـSPA على `/warehouse-v2` يعرض **إشعار صيانة** (503) والواجهة القديمة على `/` تعمل كاملةً.
- **mutations الـv2 ترجع 503 V2_DISABLED** → النظام القديم يصبح الكاتب الوحيد (لا كتابة مزدوجة).
- قراءات v2 تبقى متاحة (لوحات القراءة لا تنكسر).
- ⚠️ **قيد مهم:** الأصناف التي فُعِّل عليها `tracking_mode` تبقى ممنوعة من مسارات الكتابة القديمة (WRITER_NOT_LOT_AWARE) — هذا مقصود لحماية ثبات الدفعات. إن كان لا بد من تحريكها أثناء التعطيل: أعد الوضع بـ`UPDATE inv_items SET tracking_mode='none' WHERE id=?` **بعد** توثيق القرار (يفقد إلزامية تتبّع الدفعة لذلك الصنف، ولا يحذف بيانات الدفعات).

## الدرجة 2 — تراجع بالكود (دقائق)

1. انشر الـcommit السابق للترقية (مسجَّل في manifest الإصدار + `GET /api/version`).
2. المخطط الجديد (أعمدة/جداول الدفعات، الفهرس المركّب) **يبقى** — إضافي وغير مُعطِّل للكود الأقدم (الكود القديم يتجاهله).
3. تحقّق: `/api/version` يعكس الـcommit القديم + الواجهة القديمة تعمل + `npm run warehouse:v2:preflight` (على أدوات نسخة RC إن لزم) لتوثيق حالة البيانات لحظة التراجع.

## الدرجة 3 — استعادة قاعدة البيانات (الملاذ الأخير)

> فقط عند فساد بيانات فعلي (مثال: `lot_invariant_violation_total > 0` مع انحراف preflight لا يُفسَّر).

1. أوقف الخدمة (أو `WAREHOUSE_V2_ENABLED=0` + منع الكتابة القديمة مؤقتًا).
2. استعد النسخة المأخوذة في خطوة الترقية 1 (`mariadb < backup.sql`).
3. أعد تشغيل الإصدار المطابق للنسخة، ثم `preflight` → **BLOCKER=0** قبل فتح الاستخدام.
4. المعاملات بين النسخة والحادثة تُعاد يدويًا من سجل التدقيق (`inv_tx_events` + `audit_logs` تتضمن actor/payload لكل مستند).

## متى تتراجع؟ (محفّزات مقترحة للتنبيه)

| الإشارة | المصدر | الإجراء |
|---|---|---|
| `lot_invariant_violation_total > 0` | `/api/metrics` + سطر fatal في اللوج | درجة 1 فورًا + preflight + تحقيق |
| `gl_imbalance_total > 0` | `/api/metrics` | درجة 1 + مراجعة القيود (القيد المرفوض لم يُرحَّل أصلًا — العدّاد إنذار مبكر) |
| BLOCKER في preflight بعد الترقية | `npm run warehouse:v2:preflight` | لا تفتح الاستخدام؛ عالج أو تراجع |
| `/api/inventory/v2/ready` = 503 مستمر | probe | الهجرات لم تكتمل — راجع لوج الإقلاع |
| موجة 409/429 غير طبيعية | `/api/metrics` (v2_conflicts_409) | تحقيق؛ ليست وحدها سبب تراجع |

## ما لا يفعله التراجع أبدًا

- لا يحذف جداول/أعمدة الدفعات (البيانات تبقى للاستئناف).
- لا يلمس بيانات النظام القديم (المبيعات/المشتريات/الجرد القديم غير متأثرة بنيويًا).
- لا يتطلب أي هجرة يدوية.
